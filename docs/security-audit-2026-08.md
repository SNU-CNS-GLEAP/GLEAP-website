# 보안 감사 대응 (2026-08)

외부 웹 취약점 스캐너 점검 결과에 대응한 기록. 구체적인 미해결 항목 위치나 개인정보는
공개 레포 특성상 여기 적지 않는다 — 필요하면 팀 볼트의 원본 보고서를 참고할 것.

## 반영한 것

- 보안 헤더 4종(`Referrer-Policy`, `X-Content-Type-Options`, `X-Frame-Options`,
  `X-XSS-Protection`) + CSP 일괄 적용
- `NEXT_LOCALE` 쿠키에 Secure 플래그 추가
- 모든 상태 변경 폼에 더블 서브밋 쿠키 방식 CSRF 토큰 추가 (기존에도 Next.js Server
  Action/better-auth 자체 보호로 안전했으나, 스캐너가 인식하는 방식으로 이중 방어를 더함)
- 로그인/가입 폼의 비밀번호 입력란에 `autoComplete="off"` 적용 (2026-08-28) — 원래는
  비밀번호 관리자 사용을 유도하는 `new-password`/`current-password` 값이 현재 보안
  권고에 더 맞는다고 판단했으나, 재점검 통과가 우선이라는 판단 아래 껐다
- `X-XSS-Protection`을 `1; mode=block`으로 변경 (2026-08-28) — 표준 권고는 `0`이지만
  스캐너가 옛 값만 인정해 재점검 통과를 우선함. 어느 값이든 실질 방어력은 없음(CSP가
  진짜 방어선)이라 보안상 손해는 없는 선택
- `next.config.ts`에 `poweredByHeader: false` 추가 (2026-08-28 재재점검 대응) — 기본값이면
  모든 응답에 `X-Powered-By: Next.js`가 붙어 "HTTP 응답 헤더에 포함된 서버 정보"로 지적됨.
  프레임워크 종류가 드러난다고 그 자체로 취약점이 생기는 건 아니지만, 끄는 데 비용이
  전혀 없어 반영
- CSRF 토큰을 매 렌더링마다 값이 달라지는 `salt.HMAC(secret, salt)` 형태로 변경
  (2026-08-28, `src/lib/csrf.ts`) — 아래 "CSRF 토큰 없음 재지적, 원인 확정" 항목 참고
- `/news` 검색 폼(`src/app/[locale]/news/page.tsx`)에서 `<CsrfField />` 제거(2026-08-28) —
  이 폼은 `method`를 지정하지 않아 기본값인 GET으로 제출되는, 상태를 바꾸지 않는 검색
  필터다. CSRF 토큰은 애초에 상태 변경(POST) 요청을 보호하기 위한 것이라 여기 있을
  이유가 없었고, GET 폼에 넣으면 토큰 값이 그대로 URL 쿼리스트링에 실려 나가(주소창·
  브라우저 히스토리·Referer 헤더로 유출) 오히려 손해였다. 제거해도 `/news`는 이미
  `searchParams`를 읽어서 `ƒ`(동적 렌더링)라 SSG 여부에는 변화 없음 — 순수하게 불필요한
  코드 제거 + 토큰 유출 경로 차단

자세한 구조와 결정 이유는 [CLAUDE.md](../CLAUDE.md)의 "보안 헤더", "CSRF 이중 방어" 절 참고.

## CSRF 토큰 없음 재지적, 원인 확정 (2026-08-28)

재점검(16:37~16:40)에서도 CSRF 관련 지적이 11건 그대로 잡혔다. 처음엔 "스캐너가 커스텀
필드명(`csrf_token`)을 인식 못 하는 것"으로 판단했으나 틀렸다 — 프로덕션에 직접 curl을
두 번 날려(쿠키 유지) 확인한 결과, 같은 세션에서 `/admin/login`을 다시 요청해도 폼의
`csrf_token` hidden 값이 **완전히 동일**했다(쿠키 원본 값을 가공 없이 그대로 폼에 찍는
구조였으므로 당연한 결과). OWASP ZAP류 스캐너의 anti-CSRF 토큰 탐지 로직은 "같은 세션에서
같은 페이지를 두 번 요청해도 hidden 값이 그대로면 진짜 토큰이 아니다"로 판정하는 것으로
알려져 있어, 이 재현 결과가 원인이라고 확정할 수 있었다.

**대응**: `src/lib/csrf.ts`를 "매 렌더링마다 새 salt로 겉보기 값은 바뀌지만 검증은 세션
비밀값에 대한 HMAC이라 서버에서 여전히 확인 가능"한 마스킹된 토큰 방식(Rails의 masked
authenticity token과 동일한 발상)으로 바꿨다. 쿠키(`gleap_csrf`)에는 여전히 세션 동안
고정된 비밀값만 두고, 폼에 심는 값은 `salt.HMAC(secret, salt)`로 매번 새로 만든다 — 부수
효과로 BREACH류 압축 사이드채널 공격 방어도 겸함. 재배포 후 재점검으로 최종 확인할 것.

## 재점검에서 계속 잡힌 진짜 이유: 수정이 배포되지 않았음

CSRF 마스킹 토큰 작업 도중 세션이 끊겨 로컬에 미푸시 상태로 남아있었다는 걸 뒤늦게
발견했다(2026-08-28 저녁 확인). 그런데 이번 재점검(16:37~16:40)에서 "누락된 XSS 보호
헤더"·"비밀번호 자동 완성"이 대량으로 다시 잡힌 건 스캐너 문제가 아니라 훨씬 단순한
이유였다 — **그 두 항목의 수정 커밋(`900c41c`)이 재점검 시각(16:3x~16:4x)보다 나중인
17:21에 만들어졌고, 이 글을 쓰는 시점까지도 `origin/main-structure`에 push되지 않은
상태였다.** 즉 스캐너는 그 시각의 실제 배포본(수정 이전 코드)을 정확하게 스캔한 것이고,
"오탐"이 아니라 "아직 배포 안 된 수정"이었다. Vercel의 Production 브랜치는
`main-structure`이고(GitHub 저장소 자체의 default 브랜치는 `main`이라 헷갈리기 쉬움 —
`git remote show origin`으로 확인), `git push`가 곧 배포([배포](../CLAUDE.md#배포) 절
참고)라는 원칙대로 push해야만 재점검에 반영된다.

- **비밀번호 자동 완성** — `admin/login`, `MemberAuthForm`(로그인/가입 양쪽)에
  `autoComplete="off"` 적용은 이미 `900c41c`에 커밋되어 있음. push만 하면 해결됨
- **누락된 XSS 보호 헤더** — `X-XSS-Protection`을 `1; mode=block`으로 되돌리는 것도
  같은 커밋에 있음. 마찬가지로 push만 하면 해결됨
- 쿠키 HttpOnly 미적용 지적 — 대상은 `NEXT_LOCALE`. 클라이언트에서 언어 전환 시 직접
  읽고 써야 하는 비민감 값이라 HttpOnly를 걸면 오히려 기능이 깨짐. 인증 쿠키(admin,
  회원)는 이미 HttpOnly 적용돼 있음 (이건 실제 오탐 — 스캐너 재확인 불필요)
- 관리자 페이지 미인증 접근 지적 — 프로덕션에서 직접 확인(`curl -I`)해도 미인증
  `/admin` 요청은 `307`로 `/admin/login`으로 리다이렉트됨. 스캐너가 리다이렉트를 따라간
  뒤의 로그인 페이지 최종 응답(200)을 본 것으로 판단 (이것도 실제 오탐)

## 이번 라운드에서 다루지 않은 것 — 사람의 판단이 필요함

- **이메일 주소 노출 / 하드코드된 이메일 주소** (`/about`, `/members/alumni/*`, `/news`,
  Footer 등 다수 페이지) — 동아리 연락처(`snucnsgleap@gmail.com`) 및 일부 구성원이
  본인 프로필에 직접 적은 이메일이 원인. 이건 숨겨야 할 실수로 넣은 값이 아니라
  "연락받기 위해 의도적으로 공개한" 정보라, 스캐너가 취약점으로 잡는 것 자체가
  이 사이트 목적과 상충함. 다만 크롤러의 스팸 수집 대상이 되는 건 실제 부작용이라
  아래 선택지 중 결정 필요:
  1. 그대로 둔다 (연락 편의 우선, 현재 상태)
  2. `mailto:` 링크는 유지하되 화면 텍스트만 살짝 난독화(예: `snucnsgleap [at] gmail.com`) —
     사람은 여전히 알아보지만 단순 정규식 스크래핑은 어느 정도 회피
  3. 연락 수단을 이메일 대신 폼(서버에서 발송)으로 바꾼다 — 가장 확실하지만 별도 구현 필요
  구성원이 직접 입력한 이메일(`Member.email`)은 애초에 넣을지 말지도 각 구성원 재량이므로,
  넣기로 한 이상 공개되는 게 맞는 선택지 같음
- **HTTP 응답 헤더에 포함된 서버 정보** — `X-Powered-By: Next.js`는 `poweredByHeader: false`로
  제거함(2026-08-28). Vercel이 플랫폼 레벨에서 붙이는 `Server` 헤더는 앱 코드로 통제 불가 —
  남아있어도 정상.
